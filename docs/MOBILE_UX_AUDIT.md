# Cura dynamic UX audit

## Scope and current architecture

This is an audit of the current implementation, not a redesign. No production UI was changed.

Cura currently has one rendered application component, `App` in `src/App.tsx` (2,984 lines). It owns canvas state, persisted-state loading and saving, selection, pointer gestures, menu/modal state, import, sharing, sizing, budget, presentation, formatting, and notifications. Supporting `src/*.ts` modules are pure domain helpers: `boardUx.ts`, `presentation.ts`, `sharing.ts`, `importQuota.ts`, `sizeConversion.ts`, `imageProcessing.ts`, and `commerceRegistry.ts`. There are no separate UI component files or custom UI hooks.

The persisted canvas remains the `Board` payload in `localStorage` under `cura-link-only-board-v3`; item/board coordinates, scales, board bounds, presentation, style overrides, decorations, budgets, and sharing metadata are all stored in that existing model. User settings, sizing migration, quota, exchange-rate cache, and saved/shared collection state have their own keys. The responsive phase must not replace or reinterpret those payloads.

## Current responsive model

| Behavior | Current implementation | User consequence |
| --- | --- | --- |
| Continuous adaptation | Canvas is `100vw × 100vh`; overlay widths often use `min()`/`max-width`; measured item/header heights use `ResizeObserver`. | Some text wrapping is accommodated inside boards, but the application shell does not reserve usable space for its own fixed UI. |
| Width switches | CSS switches at 760, 720, 680, and 520px; the only input query is `@media (hover: none)`. | The app has a few narrow-width patches, not geometry-based layout states. 713px and 913px can behave unlike their available space suggests. |
| Height switches | Only individual max-heights use `vh`/`dvh`; there are no height media queries or shell states. | Short landscape windows can have the same top chrome and floating panels as tall windows, leaving little canvas. |
| Input switches | Pointer Events are used; `touch-action: none` is applied to the canvas and movable objects. Hover only reveals/enhances some controls. | Touch is technically received but does not get a touch-first interaction model; native pinch/scroll is suppressed. |
| Overlay geometry | Menus clamp only at initial opening through `window.innerWidth/innerHeight`; most panels use fixed corners. | A resize, orientation change, or virtual keyboard can leave an open menu/panel covering controls or positioned under browser UI. |
| Container responsiveness | No `container-type` or `@container` rules. | Inspector, board controls, grids, and modal content react to viewport width only, not their actual available inline/block size. |

There is no user-agent detection, `matchMedia`, visual-viewport handling, or JavaScript resize listener. This avoids UA-specific behavior, but means layout-derived JavaScript such as `fitCanvas`, new-board placement, paste placement, and floating-menu clamping uses raw `window.innerWidth/innerHeight` rather than the canvas’s remaining rectangle.

## Fixed geometry, layering, and CSS inventory

Important hard geometry in the current UI includes: canvas `100vw/100vh`; world `5200×3600`; sticker width 218px and initial art height 244px; inspector 260px; quick add 310px; top bar 52px then 56px minimum; zoom controls 32×30px; add control 48×48px; product delete/open 20/23px; resize handles 17px (34px for `hover:none`) and 28px; template gallery up to 390px; format toolbar up to 520px; match modal up to 920px; closet up to 420px.

The only media queries are `max-width:760px`, `720px`, `680px`, `520px`, `hover:none`, and `prefers-reduced-motion`. There are no `pointer:coarse`, `pointer:fine`, `hover:hover`, orientation, aspect-ratio, height, safe-area, container, or reduced-transparency rules. Existing `dvh` use is limited to a few modal/menu/panel max-heights; `100vh` remains on the app shell, canvas, match modal, shared view, and inspector.

## Validation priorities

The most revealing initial checks are 320×568, 375×667, 390×844, 487×800, 713×700, 768×1024, 1024×600, 1180×820, 1280×650, 1366×768, 1920×1080, and a 2560-wide window. Every check should be performed with: a selected product, an active board, a long board inspector, a formatting toolbar, a menu near an edge, a modal with the virtual keyboard open, and persisted content before/after resize/orientation.

The full matrix in the product brief remains the acceptance matrix; odd widths are mandatory because current breakpoints only cover a small set of viewport thresholds.

## Implementation status after shell/navigation batch

This document records the pre-responsive baseline, not a fresh audit of the modified UI. Batch A replaced the app/canvas viewport and safe-area assumptions and introduced responsive tokens. Batch B replaced the wrapping topbar with a one-row, container-query-driven action hierarchy: New board and a bounded More surface remain available on compact widths; Pan now sits beside Zoom/Fit; Fit uses the canvas and control rectangles; the empty-state instruction points to the visible Add control. The fixed inspector, object action menus, drag/touch behavior, and overlay focus policy described above remain open for later batches. See `DYNAMIC_UI_ARCHITECTURE.md` and `MOBILE_IMPLEMENTATION_PLAN.md` for implemented details and remaining sequencing.

The later canvas + multi-input pass has now addressed several interaction rows above: taps no longer commit object movement; blank taps no longer start visible zero-size lassos; pointer cancellation/lost capture clean up and roll back object manipulation; nested controls do not start parent drags; touch multi-selection has a labeled command; wheel/trackpad pans the canvas; selected product/board editors expose more non-drag commands; and coarse selected-object hit areas are enlarged. The table remains a pre-change baseline. Custom canvas pinch, full inspector/sheet adaptation, some board overlap/z-order actions, extreme-zoom handle size, and real-device input validation remain open.

## Adaptive inspector/editor implementation follow-up

The inspector limitation recorded above has been addressed in the adaptive inspector/sheet/editor batch. Product, board, board-element, and multi-selection editing continue to use the same `App.tsx` state and content; `src/styles.css` now presents that inspector as a compact bounded sheet, a medium transient pane, or an expanded side lane when both width and height permit. Product formatting, task dialogs, template/saved surfaces, contextual menus/popovers, and closet follow related safe-area and dynamic-height rules. No persisted data or business semantics changed.

Headless CSS geometry checks across compact through ultrawide dimensions, short heights, and coarse/fine pointer emulation passed for viewport containment, contained scrolling, reachable dialog close/confirm actions, non-overlapping selection actions and inspector, and no horizontal page overflow. This does not substitute for real-device virtual-keyboard, safe-area, focus-trap/return, or screen-reader testing. See the architecture and plan documents for the exact matrix and remaining work.
